# Барвиха Невский - навигация по проекту

Этот документ - карта проекта. Читай его в начале каждой сессии, чтобы понимать, где что лежит и как с этим работать.

👉 **Начинаешь новую сессию — открой `СЛЕДУЮЩАЯ-СЕССИЯ.md` в корне.** Там коротко: на чём остановились, что выложено в бой, а что готово и ждёт, и три вещи, о которые спотыкаются в первые же минуты. Файл живёт в одном экземпляре — в конце сессии его переписывают под её итог.

## Что это за проект

**Барвиха Невский** - ресторан с премиум-кальянами на Невском проспекте, 26 (дом Гансена, Санкт-Петербург).

Проект решает задачу: создать среду, которая помогает максимально быстро и полно решать все вопросы, связанные с работой этого бизнеса — от продукта и аудитории до маркетинга и целей роста.

Подробности - в `.business/INDEX.md`.

## Ключевые принципы проекта

1. Премиальность и статус во всём — от продукта до коммуникации.
2. Сервис и атмосфера важнее одного «хитового» продукта.
3. Решения опираются на данные из `.business/` (сезонность, каналы, цели), а не на догадки.

## Стек

- **Приложение:** Next.js 16 + React 19 + Tailwind 4 + TypeScript, папка `mini-app/`
- **Хостинг:** Amvera Cloud, регион Москва. **Опубликовано 01.08.2026: https://chaevye-borzovavv.amvera.io** Сборка из `Dockerfile` + `amvera.yaml` в корне. Состояние базы видно на `/api/health`

⚠️ **Выкладка = простой.** Пока Amvera пересобирает контейнер, приложение отвечает **503 «С приложением что-то не так»** — проверено 02.08.2026, простой длился несколько минут. Поэтому «не выкладывать во время смены» — правило не про тестовые данные, а про то, что в эти минуты администратор физически не сможет внести чаевые. Смена идёт примерно с 16:00 до 06:00, значит окно для выкладки — днём.

⚠️ **Как выкладывать.** Amvera собирает только из ветки `master`. Подключение к GitHub настроено, но **срабатывает не всегда** — 02.08.2026 одна выкладка не доехала, в бою осталась предыдущая версия. Поэтому отправлять надо напрямую и потом проверять:

```bash
cd "/Users/user/Documents/Невский" && git branch -f master main && git push origin main && git push origin master && git push amvera master
```

Затем сверить, что в бою нужный коммит: `git ls-remote --heads amvera` должно совпасть с `git log --oneline -1 master`.
- **База данных:** PostgreSQL 17 на Amvera, проект `chaevye1`, регион Москва — **подключена 01.08.2026**. Доступ в `mini-app/.env.local`, в git не уходит. Схема и настройка: `mini-app/scripts/`, команда `npm run db:setup`

⚠️ **Боевые и тестовые данные разделены схемами одной базы.** Права завести вторую базу у пользователя нет, поэтому: боевые данные — в схеме `public`, проверки — в схеме `test`. Переключает переменная `DATABASE_SCHEMA` в `mini-app/.env.local` (там стоит `test`). На сервере Amvera она не задана, поэтому в бою всегда `public`. **Никогда не проверять изменения на боевой схеме** — там настоящие деньги смены.
- **База для проверок:** PostgreSQL 17 прямо на компьютере владельца, Postgres.app, база `chaevye` — **заведена 04.08.2026**. Слушает только этот компьютер, наружу не смотрит, пароля не требует. Данных ресторана в ней нет и не будет: только выдуманные записи.

⚠️ **С компьютера владельца боевая база недоступна.** На Маке работает VPN **incy** (движок xray, узел в Нидерландах). Он подменяет адреса: имя базы разрешается в служебный `240.0.x.x`, соединение на порт 5432 принимается перехватчиком и до Amvera не доходит. HTTPS при этом ходит нормально, поэтому `/api/health` отвечает, а база — нет. Диагностика: `nslookup` на адрес базы даёт `240.*` вместо `51.250.35.206`; стук в несуществующий адрес `203.0.113.9` «успешен» — верный признак, что соединения перехватывает что-то локальное. Попытка добавить `amvera.tech` в исключения профиля «Bypass LAN» результата не дала (04.08.2026).

**Следствие, которое надо принять:** проверки идут на локальной базе, а всё, что должно писать в боевую, живёт на сервере. Строка подключения к Amvera сохранена в `mini-app/.env.local` закомментированной.
- **Мобильный интерфейс:** Telegram Mini App (ещё не подключён)
- **Данные по чекам:** Quick Resto API

Определён 31.07.2026 в рамках плана учёта чаевых (см. `plans/`). Хостинг и база пересмотрены 01.08.2026: вместо Vercel и Supabase — российские серверы, потому что в базе персональные данные сотрудников. Обоснование и что нельзя упустить при заведении — в плане, раздел «A1. Хранилище».

## Как работать с проектом

- Перед любой задачей - прочитай этот файл, затем нужные документы из `.business/` и `plans/`.
- Если меняется бизнес-логика - обнови `.business/INDEX.md` и нужные файлы.
- Если меняется технический план - обнови соответствующий план в `plans/`.
- Если появляется новая важная папка или документ - обнови этот `CLAUDE.md`.

## ВАЖНО: план для каждой новой функции

Любая функция, которую мы создаём в любом чате, всегда оформляется планом в папке `plans/`.

Правила:
1. Один план = одна функция. Если план уже есть - работаем с ним.
2. Имя файла: `YYYY-MM-DD-название-функции.md`.
3. План делится на фазы. У каждой фазы статус `[ ]` или `[x]`.
4. В конце плана - итоговый блок: реализован целиком или нет, что осталось.
5. Любой агент обязан актуализировать план после каждой сессии.

## ВАЖНО: завершение каждого чата

В конце каждой сессии записывай рефлексию в файл `.business/история/YYYY-MM-DD-краткое-название.md` (создавай папку при необходимости).

Формат:
1. Какая задача была поставлена.
2. Как я её решал.
3. Решил ли - да / нет / частично.
4. Эффективно ли решение, что можно было лучше.
5. Как было и как стало.
