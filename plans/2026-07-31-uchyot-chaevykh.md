# Учёт чаевых

*План создан 31.07.2026. Задача: свести учёт чаевых из трёх источников в одно место и убрать бумагу.*

## Проблема

Сегодня учёт чаевых устроен так:

| Источник | Куда идут деньги | Как учитывается сейчас |
|---|---|---|
| Терминал при оплате (эквайринг) | на счёт ресторана | вручную |
| QR Сбер Чаевые на чеке | сразу на карту сотрудника | никак / вручную |
| Наличные | в руки | **на бумаге**, потом переносятся в Google Таблицу |

Следствия, видные из [`../.business/economics/tips.md`](../.business/economics/tips.md):
- сервисный сбор перестал вноситься с 1 июня 2026 — потеря ~3 300 ₽/день из учёта;
- выручка не заполнялась 25 месяцев из 27, метрика «% чаевых от выручки» не работала ни разу;
- формула итога отсекала хостес.

Все три проблемы — от ручного ввода. Их не чинят инструкцией, их чинят системой.

## Что делаем

Telegram Mini App для администратора: в момент расчёта с гостем ввести **номер стола и сумму наличных чаевых** за два нажатия.

### Ключевая идея

**Номер стола — ключ ко всему остальному.** Quick Resto знает по столу: время закрытия счёта, сумму чека, официанта. Значит вводить нужно только два числа — стол и сумму. Остальное система подтягивает сама.

Больше того: приложение может показать **список только что закрытых счетов** и администратору останется тапнуть по нужному. Ни поиска, ни набора текста.

### Как выглядит экран

```
┌─────────────────────────────┐
│  Чаевые · смена 31 июля     │
├─────────────────────────────┤
│  Стол 12 · 8 400 ₽          │
│  Анна · 21:47          →    │
├─────────────────────────────┤
│  Стол 4 · 21 300 ₽          │
│  Марина · 21:31        →    │
├─────────────────────────────┤
│  Стол 9 · 5 900 ₽           │
│  Анна · 21:12          →    │
├─────────────────────────────┤
│      + Другой стол          │
├─────────────────────────────┤
│  За смену: 4 300 ₽ · 9 зап. │
└─────────────────────────────┘
```

Тап по счёту → цифровая клавиатура → сумма → «Готово». Внизу всегда виден итог смены: администратор сразу видит, что запись прошла. Именно этого нет у бумаги, и именно поэтому там теряются данные.

«Другой стол» — запасной путь, если счёт ещё не закрыт или стола нет в списке.

| Что | Чем | Почему |
|---|---|---|
| Приложение | Next.js | это то, что осваивается в практикуме — задача учебная и рабочая одновременно |

Номера стола в выгрузке нет. Зато есть время до секунды и точная сумма чека — этого достаточно, чтобы однозначно найти чек в Quick Resto, а через него получить и стол, и официанта. Такой ключ даже надёжнее номера стола: его не надо никому вводить руками.

**Смена ≠ календарный день.** Работа с ~16:00 до ~06:00, пик 01:00–04:00 (53 % транзакций). В отчёте дата календарная, поэтому ночь падает на следующее число. Без пересборки данные противоречивы: за 27 июля Сбер показывает 28 470 ₽ при 22 828 ₽ всех чаевых за день. С границей смены **06:00** противоречие исчезает везде. **Только одна команда получает деньги.** Все 447 транзакций — «Официант 1». Ни одной по QR, ни одной по остальным девяти командам. Требует выяснения: выгрузка была с фильтром или все терминальные чаевые действительно идут в один котёл?

**Адрес заведения:** `https://fk381.quickresto.ru`. API включён — запрос без авторизации отвечает `401`, а не `404`.

**Доступ.** Back Office API (версия 2.92) работает по **Basic-авторизации**, но **у API отдельные логин и пароль** — не те, что у входа в бэк-офис. Проверено 31.07.2026: учётные данные веб-входа дают `401` с пустым телом ответа.

Задаются в бэк-офисе: **Предприятие → Настройки → вкладка «Общие настройки» → «Логин и пароль для API»**. Если поля пустые, значения придумываются и сохраняются там же.

```bash
curl -u "логин:пароль" "https://<адрес>.quickresto.ru/api/list?moduleName=front.orders&className=ru.edgex.quickresto.modules.front.orders.OrderInfo"
```

**Нужные поля в объекте чека** (`ru.edgex.quickresto.modules.front.orders.OrderInfo`):

| Поле | Назначение |
|---|---|
| `localCreateDate` | время чека — ключ склейки со Сбером |
| `frontTotalPrice` | сумма чека — второй ключ склейки |
| `table.title` | номер стола |
| `waiter.fullName` | официант |
| `cashier` | кассир |
| `frontTotalCashMinusDiscount`, `frontTotalCard`, `frontTotalBonuses` | разбивка оплаты |
| `shiftId` | идентификатор смены |
| `documentNumber`, `id` | идентификаторы чека |

**Граница смены решена кассой.** Поле `shiftId` и отдельный модуль «Кассовые смены» (`front.zreport.Shift`) означают, что придуманная граница 06:00 не нужна — берём настоящую смену из Quick Resto. Правка к Фазе 0.2.

**Безопасность доступа:** заводим отдельного пользователя с правами только на чтение, учётные данные держим в `.env`, в репозиторий не коммитим.

**Риск:** возможно, API открыт не на всех тарифах. Диагностика — ошибка 401 на первом запросе, решение — `support@quickresto.ru`.

### [~] Фаза 3. Отчёты — формат согласован 01.08.2026

**Структура, согласованная с владельцем:**

| Раздел | Содержание |
|---|---|
| Сколько оставили гости | три блока официантов: наличные, терминал, сервисный сбор — раздельно, как в приложении |
| Кто сколько получил | четыре блока «на руки»: официанты, администраторы, кассиры, хостес |
| Кальянный бар | отдельный контур, в зал не входит |
| Сводная | по дням: виды денег, общий чай, распределение по получателям, **расхождение**, % от выручки, выручка |

Строка **«Расхождение»** = общий чай − итого распределено. Должна быть нулём; в ячейке настроен формат, при котором ноль показывается прочерком, а ненулевое — красным. Это защита от потери или задвоения денег.

**Исправлена ошибка рабочей таблицы:** там `Общий чай всего` считает `=SUM(B2:B102)` и отсекает хостес. В дубле итог складывает блоки поимённо, отвалиться никто не может.

**Дата смены:** подтверждено, что смена пишется на дату **начала**. Ночь с 31 июля на 1 августа целиком идёт на 31 июля. Приложение уже так и считает — граница бизнес-дня 11:00.

Проверено на примере: общий чай 5 300 ₽ = на руки официантам 4 252,50 + администратору 860 + кассиру 187,50. Расхождение ноль.

**Выгрузка сделана 01.08.2026.** Цепочка из трёх шагов:

1. **Приложение** → кнопка «Выгрузить смену для отчёта» на экране итогов → файл `смена-ГГГГ-ММ-ДД.json`. Код: [`exportShift.ts`](../mini-app/src/lib/exportShift.ts).
2. **[`../scripts/report_new.py`](../scripts/report_new.py)** — создаёт пустой отчёт на месяц. Без аргументов берёт текущий, иначе `2026-09`.
3. **[`../scripts/report_fill.py`](../scripts/report_fill.py)** — вписывает выгрузку в столбец нужной даты.

Скрипт сам находит столбец по дате, раскладывает суммы по блокам и **занимает свободную строку**, если фамилии в блоке ещё нет: блоки администраторов и кассиров пустые по замыслу, а состав официантов меняется. Нули не пишет. В конце показывает расхождение — если не ноль, предупреждает.

Проверено сквозняком на смене 31.07.2026: наличные, сбор и «на руки» разложились по своим блокам, администратор и кассир вписались в свободные строки, расхождение ноль.

**Для этого пришлось добавить в приложение роли смены:** администратор и кассир выбираются вместе с составом. Раньше приложение считало только суммы, не зная, кому именно они уходят, а отчёту нужны конкретные строки. Роли необязательны — без них ввод работает, но отчёт придётся дозаполнять руками, о чём приложение предупреждает.
