# Отметка о выгрузке смены

*Начат 10.08.2026 по замечанию владельца: «когда выгружаешь смену, непонятно,
выгрузился отчёт или нет — должно быть подтверждение для администратора».*

## Что было не так

Кнопка «Выгрузить смену для отчёта» собирала файл и молча роняла его
в загрузки. При **успехе на экране не менялось ничего**: сообщение показывалось
только при сбое связи или когда часть записей не ушла в базу.

Отсюда два последствия:

1. Администратор не знал, получилось или нет, и жал ещё раз.
2. Вопрос «эту смену уже выгружали?» не имел ответа вовсе — ни на следующее
   утро, ни со второго телефона.

## Что сделано

### [x] Подтверждение сразу после нажатия

`Смена выгружена · файл смена-2026-08-10.json`

Имя файла названо прямо: в папке загрузок их десятки, и «файл скачан»
без имени не помогает.

### [x] Постоянная отметка на экране итогов

| Было | Стало |
|---|---|
| «Выгрузить смену для отчёта» | «Выгрузить смену для отчёта» + подпись **«ещё не выгружена»** |
| — | после выгрузки: **«Выгрузить заново»** + **«✓ выгружена в 17:35 · Анна К.»** |

Отметка держится на экране, а не мигает сообщением на две секунды: вопрос
задают и через час, и назавтра, и часто не тот, кто нажимал кнопку.

Пока идёт сборка, кнопка занята и пишет «Собираю отчёт…» — раньше её можно
было нажать повторно и скачать два файла.

### [x] Отметка живёт в базе, а не в телефоне

Две колонки в `shifts`: `exported_at`, `exported_by`. Время ставит **база**,
а не телефон: часы на телефонах расходятся, а это отметка о денежном документе.

В памяти телефона она была бы бесполезна ровно там, где нужна: со второго
телефона и на следующий день её бы не увидели.

Повторная выгрузка перезаписывает отметку — важно, когда смену выгрузили
в последний раз, а не когда впервые.

⚠️ Если файл скачался, а отметку поставить не удалось, приложение так и пишет:
«файл скачан, но отметку в базе поставить не удалось». Говорить «не выгрузилось»
было бы неправдой — файл у человека на руках.

### [x] Приложение смены само применяет схему при старте

Понадобилось из-за этих двух колонок. С компьютера владельца боевая база
недоступна (VPN incy перехватывает порт 5432), значит применить схему может
только то, что живёт в одном дата-центре с базой.

Бэк-офис так делает с 07.08.2026; теперь и приложение смены:

```dockerfile
CMD ["sh", "-c", "node scripts/db-setup.mjs && npm start"]
```

⚠️ **Плата за это: не удалось применить схему — контейнер не поднимется,
и смена останется без приложения.** Выбор в пользу громкого отказа сделан
по образцу бэк-офиса: приложение без нужных колонок всё равно сломается,
только позже и посреди ввода денег. Причина будет видна в журнале Amvera.

Схема написана целиком через «создать, если ещё нет», выполнять можно
сколько угодно раз.

## Что проверено

| Проверка | Результат |
|---|---|
| `npx tsc --noEmit` | чисто |
| Схема применяется на локальной базе | колонки `exported_at`, `exported_by` появились |
| `npm run copies` | схема синхронизирована с бэк-офисом |
| До выгрузки | «Выгрузить смену для отчёта» · «ещё не выгружена» |
| После нажатия | сообщение «Смена выгружена · файл смена-2026-08-10.json» |
| Экран после | «Выгрузить заново» · «✓ выгружена в 17:35 · Анна К.» |
| Отметка в базе | `2026-08-10 17:35:03+03 | Анна К.` |
| После перезагрузки страницы | отметка на месте — читается из базы, а не из памяти |

## Итог

**Реализовано целиком, в бою НЕ выложено.** 10.08.2026 смена уже шла, а эта
выкладка вдобавок впервые применяет схему при старте — проверять такое
во время смены нельзя.

Выкладывать утром, в окне 7:00–11:00. После выкладки убедиться, что
в журнале Amvera схема применилась и приложение поднялось.

## Что это открывает дальше

Дата выгрузки — то, чего не хватало для пометки «смену тронули **после**
выгрузки». См. `plans/2026-08-03-upravlencheskiy-blok.md`, фаза 3.5: метка
«правлено» там есть, но она про сам факт правки, а не про правку задним
числом после сдачи отчёта. Теперь дату есть с чем сравнивать.
