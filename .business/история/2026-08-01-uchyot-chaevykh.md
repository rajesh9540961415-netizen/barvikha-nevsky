# Учёт чаевых: от разведки до работающего приложения

*Сессия 31.07–01.08.2026.*

## 1. Какая задача была поставлена

Автоматизировать учёт чаевых. Исходно — два контура: безнал через терминал и наличные, которые ведутся на бумаге. Требовалось придумать, как администратору удобно вносить номер стола и сумму наличных в момент расчёта с гостем.

По ходу задача выросла: добавились сервисный сбор, расчёт деления между официантами, администратором и кассиром, и заполнение месячного отчёта.

## 2. Как решал

**Сначала разведка, потом код.** Не начинал писать, пока не выяснил, что вообще доступно:

1. Зашли в ЛК Сбер Чаевые — оказалось, там оба контура безнала и есть выгрузка отчёта.
2. Разобрал выгрузку: 447 транзакций, нашлись пресеты терминала и соотношение наличные/безнал.
3. Подключился к Quick Resto API — три ошибки на пути, все нашлись через официальную спецификацию OpenAPI.
4. Только потом — приложение на реальных данных: 48 столов, 17 сотрудников из кассы.

**Правила выяснял до реализации, а не после.** Каждый раз, получив правило от владельца, показывал его на числах и переспрашивал там, где мог понять двояко. Дважды это спасло от неверной формулы.

## 3. Решил ли — частично

**Сделано:**
- приложение: ввод по столам и залам, три вида денег, официант и ответственный в каждой записи, состав смены с ролями;
- расчёт деления по правилам заведения;
- месячный отчёт и выгрузка в него из приложения;
- проект под git и на GitHub.

**Не сделано:** общее хранилище. Данные живут в памяти браузера на одном компьютере. Упирается в решение владельца — персональные данные сотрудников на зарубежных серверах.

## 4. Эффективно ли, что можно было лучше

**Что сработало:**

- **Разведка перед кодом.** Если бы начал с приложения, построил бы ввод по номеру стола — и получил бы неверные данные с первого дня, потому что номера столов повторяются между тремя залами. Это вскрылось только при чтении схемы из Quick Resto.
- **Проверка правил на числах.** Показывал пример расчёта и спрашивал. Владелец один раз сказал «я тебя обманула» и уточнил формулу — без примера ошибка ушла бы в код.
- **Спецификация вместо угадывания.** С Quick Resto API потратил несколько попыток на перебор, пока не скачал OpenAPI — там базовый адрес был написан прямо. Надо было начать с этого.

**Что можно было лучше:**

- **Слишком долго перебирал вслепую** с `front.orders`: семь вариантов записи фильтра, прежде чем проверил другие модули и понял, что дело в правах, а не в синтаксисе. Сравнение с соседними модулями стоило сделать вторым шагом, не десятым.
- **Придумал границу смены 06:00**, хотя Quick Resto хранит настоящую в настройках (11:00) и отдаёт `shiftId`. Выдумывать то, что можно спросить у системы, — плохая привычка.
- **Эксперимент с пресетами терминала не запущен.** Единственный пункт, который приносит деньги без разработки (+61 тыс. ₽/мес оценочно), назван 31 июля и до сих пор висит. Стоило настойчивее его выделять.

## 5. Как было и как стало

| | Было | Стало |
|---|---|---|
| Наличные чаевые | на бумаге, перенос в таблицу раз в месяц | ввод в приложение за два нажатия |
| Разбивка по видам | одна сумма | наличные, терминал, сервисный сбор раздельно |
| Кто получил | неизвестно до конца месяца | видно сразу, с раскладкой по каждому |
| Деление | считалось руками | считается автоматически, сходимость проверяется |
| Выручка | не заполнялась 25 месяцев из 27 | читается из Quick Resto по сменам |
| Отчёт | заполнялся вручную | заполняется из выгрузки одной командой |
| Ошибка в формуле итога | отсекала хостес | итог складывает блоки поимённо |

**Главная находка не про код.** В отчёте Сбера видно: терминал предлагает 9/14/18 %, и 71 % гостей жмут первую кнопку. Сумма чаевых определяется не щедростью гостя, а числом на первой кнопке. Подъём до 10/15/20 % даёт оценочно +61 тыс. ₽ в месяц и не требует ни строчки кода.
